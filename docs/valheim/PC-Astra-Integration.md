# PC 실행 지시: Claude 구현 → Astra 검증 무인 루프 통합

작성일: 2026-10-26 (한국 시간). 사용자가 PC의 ChatGPT Work에서 이 문서를 읽고 실행하도록 요청할 때 적용한다.
이 문서를 올리는 것 자체는 루프 재개 지시가 아니다. 멈춤 파일은 그대로 둔다.

## 실행 요청

이 저장소의 최신 무인 루프와 합의 문서를 읽고, Claude 구현 → 로컬 Codex Astra 검증 분업을 구현·연결·검증한다.
사용자는 Astra 호출이 가능하다고 확인했다. 판단이 필요한 검증 모델은 Astra이며 임의로 가벼운 모델로 바꾸지 않는다. 단순 시험 실행·대기·결과 파싱에는 Astra나 다른 모델을 호출하지 않는다.
실제 CLI 모델 식별자·호출 방법은 PC의 설정과 실행 결과로 확인하고 추측해서 넣지 않는다.
ChatGPT는 Plus로 알려져 있으나 PC 로그인 상태는 직접 확인한다. 로그인이나 권한이 필요한 경우에만 사용자에게 구체적으로 요청한다.
이 통합 구현은 PC의 GPT 작업자가 시작해도 된다. 통합 이후 모드 개발에서는 Claude가 구현하고 Astra는 검증한다.

## 먼저 확인

- CLAUDE.md 및 존재하는 AGENTS.md, docs/valheim/decisions.txt의 2절 GPT 검증 분업, progress.txt의 지금·다음, Errors.txt.
- docs/valheim/loop-plan.txt, scripts/vh-loop.ps1, vh-loop-prompt.txt, vh-reply-prompt.txt, vh-loop-restart.ps1, valheim-test.ps1.
- 현재 브랜치·HEAD·로컬 미커밋 변경·stash·실행 중인 루프/작업자/게임. 기존 작업을 덮어쓰거나 버리지 않는다.
- 동일한 통합 작업을 다른 세션이 시작했는지 확인한다. 수정 주체는 한 명이며, 기존 회차를 안전하게 마친 뒤 넘겨받는다.
- 로컬 명령 실행과 저장소·게임 경로 접근 여부를 실제로 확인한다. GitHub 연결만 가능하면 PC 실행 시험까지 했다고 보고하지 않는다.

## 구현 순서

1. 기존 합의대로 Claude 회차별 입력·출력·캐시 사용량, 턴 수, 경과 시간을 기록한다. 실제 출력에 없는 수치는 지어내지 않고 미확인으로 남긴다. 답 전용 세션은 별도로 구분한다.
2. progress.txt 순서대로 기존 변경분 게임 시험과 호위병 작업을 진행하며 기준 5~10회차를 모은다. 최신 문서가 정한 진입 조건을 따른다. 횟수만으로 절약 효과를 단정하지 않는다.
3. Claude가 구현·시험 코드를 작성하고 빌드·Core 테스트를 통과한 커밋과 필요한 게임 시험 목록을 인계하도록 연결한다.
4. 루프 스크립트가 게임 시험을 실행하고 결과·원본 로그를 보존한다. 시험 대상 커밋과 실행한 DLL의 대응을 확인한다. 환경 불량·중도 종료·누락된 결과를 PASS로 취급하지 않는다.
5. Astra는 해당 커밋의 diff와 관련 코드, 시험 조건·기대값을 리뷰하고 FAIL 원인을 분석한다. 검증 중 Claude는 다음 코드 수정을 하지 않는다.
6. 실패는 재현 조건·기대 결과·실제 결과·파일 위치·로그 근거를 Claude에 넘긴다. Claude 수정 후 다시 검증한다. 구현과 검증을 한 논리 회차로 묶어 진척·연속 FAIL·무진척 중단 규칙을 유지한다.
7. Astra 한도나 오류 시 기존 Claude 구현·시험·수정 방식으로 복귀한다. 확정된 차단 결함은 넘기지 않고 비차단 항목은 진행한다. 모든 실행 대상이 사용 불가일 때 기존 대기·깨우기 정책을 적용한다.
8. 유사한 작업 종류끼리 분업 전후의 Claude 사용량·회차 시간·재작업을 비교하고 history.md에 보고한다.

## 검증 규칙

- 최신 decisions.txt와 사용자 요구가 기준이다. 사용자 결정을 바꾸자는 의견은 결함과 구분한다.
- 코드로 확인한 사실, 실행으로 재현한 사실, 미확인 가설을 구분한다. 게임 내부 동작에 의존하는 주장은 실제 게임 코드 또는 확인된 근거를 확인한다.
- 복제·소실·저장 손상·복원 실패뿐 아니라 명령 불이행, 무한 반복, 수량 미달 완료, 잘못된 시험 기대값도 검토한다. 스타일 지적은 제외한다.
- Astra가 제안한 재현 조건·기대 결과도 요구사항에 비추어 검토 대상이다. 근거 있는 반박을 허용한다. 모델의 승인 자체를 증거로 삼지 않는다.
- 가설만으로 루프를 막지 않는다. 확정된 차단 문제는 모델 한도와 무관하게 유지한다.
- 검증자는 본체 코드를 수정하지 않는다. 검증 전 상태와 후 상태를 비교해 허용한 결과 파일 외 변경을 감지한다. 기존 미완성 변경을 무조건 reset/clean으로 지우지 않는다. 위반 시 증거와 변경을 보존하고 검증을 무효 처리한다.
- 테스트 실패 원본 로그는 재실행 전에 보존한다. 재실행 PASS만으로 처음 FAIL을 없애지 않는다.
- 한도·인증 오류·일반 실행 실패·시간 초과를 구분한다. 실제 Codex 출력과 종료 동작으로 처리하며 미확인 한도 해제 시각을 지어내지 않는다.
- 회차 사이 재시작에도 인계 커밋·단계·결과가 보존되고 중복 작업이 발생하지 않게 한다.

## 하네스 보강 및 모델 사용 배분 (사용자 추가 요청 2026-10-26)

이 절은 PC 통합 작업에 포함한다. 기존 기능을 먼저 확인하여 이미 되는 부분은 재구현하지 않는다. 별도 범용 플랫폼으로 확대하지 않고 현재 루프에 필요한 최소 기능만 보강한다.

### 역할과 호출 조건

| 작업 | 담당 | 호출 조건 |
|---|---|---|
| 구현·시험 코드 작성·수정 | Claude | 기존 회차 및 검증에서 반환된 수정 작업 |
| 빌드·Core 테스트 실행 | 스크립트/CLI | 작성 단계에서 실행, Claude가 오류를 해결하고 통과시킨 후 인계 |
| 정해진 게임 시험 실행·대기·종료·로그 보존 | 루프 스크립트 | 인계된 시험 계획대로 실행. 모델 세션을 대기용으로 유지하지 않음 |
| PASS/FAIL/환경 불량/중단/결과 누락 분류 | 루프 스크립트 | 기존 시험 출력 규약과 종료 상태로 판정. 인식 불가를 PASS로 처리하지 않음 |
| 코드 및 시험 기대값 리뷰 | Astra | 아직 리뷰하지 않은 코드·시험 변경 커밋과 관련 경로. 테스트가 PASS해도 필요한 코드 리뷰는 생략하지 않음 |
| 새 FAIL·예외·상태 불일치 원인 분석 | Astra | 판단이 필요한 새로운 증거가 있을 때. 사실과 가설을 구분 |
| 동일 실패의 반복 집계·한도 교대·상태 기록 | 루프 스크립트 | 정해진 규칙대로 처리. 의미 판단이 필요한 경우만 모델에 인계 |

- 단순 시험을 가벼운 GPT 모델로 넘기지 않는다. 모델이 아예 필요 없는 실행은 스크립트로 처리한다.
- 같은 커밋·같은 검토 범위의 완료된 리뷰를 재호출하지 않는다. 코드/시험/관련 요구사항이 바뀌거나 새 증거가 생기면 관련 부분을 다시 검토한다.
- 문서만 바뀌고 게임 동작·실행 규칙·시험 의미에 영향이 없는 경우는 Astra 호출 없이 기존 방식으로 처리한다. 루프 지시문이나 시험 기준 변경을 단순 문서로 보아 검토에서 제외하지 않는다.
- 동일 FAIL 반복은 기존 기록과 대조한다. 같은 문구만으로 같은 원인이라고 단정하지 않는다. 새 증거가 없으면 똑같은 분석을 무제한 재요청하지 않고 기존 중단/심층 조사 규칙을 적용한다.
- 게임 시험 실행 결과와 코드 리뷰 결과는 별도 칸으로 보존한다. 스크립트의 PASS는 시험 통과이며, 코드 리뷰 완료를 대신하지 않는다.
- 가능한 스크립트 시험·결과 수집은 모델 한도와 독립적으로 완료한다. 필요한 모델 단계가 남고 사용 가능한 실행 대상이 없을 때 안전한 중단 지점에서 기존 대기·절전 정책을 적용한다.

### 이번 통합과 함께 넣을 핵심 세 가지

1. **중단 지점 복원**
   - 작업 ID, 검증 커밋, 현재 단계(구현/빌드/시험/리뷰/수정 대기/완료), 시험 묶음과 완료 결과, 다음 행동을 지속 저장한다.
   - 성공 결과와 그 근거가 함께 저장된 단계만 재사용한다. 실행 중 끊긴 단계는 완료로 간주하지 않는다.
   - 재시작·한도 교대 뒤 이미 유효하게 끝난 단계를 반복하지 않는다. 별도 모델을 띄우기 전 이전 프로세스와 자식 작업·게임의 상태를 확인한다.
   - A→B→B 같은 연속 시험은 묶음이 검증 단위다. 환경을 복원할 근거가 없으면 중간부터 이어서 PASS 처리하지 않고 묶음을 재실행한다. 재시작 시험 1→2의 월드 보존 조건도 유지한다.

2. **검증 대상 고정**
   - 커밋 SHA, 실제 실행 DLL 해시, 게임 DLL 버전/해시, 시험 목록·설정·연속/단독 조건을 결과에 연결한다.
   - 커밋만 같아도 로컬 소스나 DLL이 다르면 동일 대상으로 보지 않는다. 검증 대상은 구현 인계 후 고정하고 검증 중 수정하지 않는다.
   - 코드·시험·게임 버전·환경 조건이 달라지면 영향받는 결과를 무효화하여 필요한 범위만 다시 시험한다.
   - 시험한 빌드를 확인한 뒤 완료를 기록한다. 검증 결과만으로 다른 커밋을 완료 처리하지 않는다.

3. **인계 자료 자동 생성**
   - 작업 목적·관련 요구사항 위치, 기준/대상 커밋, 변경 파일, 빌드/Core 결과, 시험 계획과 결과, 최초 FAIL 로그, 관련 Errors ID, 미완료 단계·다음 행동을 짧은 자료로 만든다.
   - 원본 로그는 별도로 보존하고 요약에는 경로와 필요한 발췌를 넣는다. 다음 모델에 전체 저장소·전체 로그를 매번 다시 읽히지 않는다.
   - 자료와 원본에 비밀정보를 넣지 않으며 로컬 로그를 무조건 공개 저장소에 올리지 않는다.
   - 인계 파일과 결과 기록은 중간 쓰기로 깨지지 않게 교체하고, 작업 ID와 커밋이 맞는 결과만 수락한다.

### 측정하면서 최소한으로 추가할 것

4. **단계별 사용량·시간**
   - 기존 회차 측정에 구현, 모델 리뷰/분석, 스크립트 시험 시간, 인계/재시도 횟수를 구분한다. 실제 제공되는 모델별 사용량만 기록한다.
   - Claude 사용량 절감과 전체 경과 시간/총 모델 사용량을 따로 비교한다. 시험 대기 시간을 모델 토큰 비용으로 계산하지 않는다.

5. **반복 실패 감지**
   - 시험 이름·실패 내용·시작 조건·대상 버전과 기존 Errors 기록을 묶어 반복을 센다.
   - 같은 문제의 수정→재시험이 반복되면 기존 두 번 FAIL 및 심층 조사 정책과 일치하게 처리한다. 단순 재시도 횟수를 진척으로 세지 않는다.
   - 상태/인계 자료 누락, 환경 불량, 실제 기능 FAIL을 분리한다. 사소한 문구 차이로 무한 재시도하거나 다른 원인을 같은 문제로 닫지 않는다.

### 하네스 자체의 완료 시험

- 동일 작업을 재시작했을 때 완료 단계가 불필요하게 다시 실행되지 않는지, 중간 결과를 PASS로 오인하지 않는지 확인한다.
- 커밋 또는 DLL 불일치 시 결과를 수락하지 않는지 확인한다.
- 모델 한도/오류, 게임 비정상 종료, 결과 누락을 통제된 조건으로 확인하고 기존 미완성 작업을 보존하는지 확인한다.
- 순차 실행과 기존 정지 규칙을 유지한다. 작업자 증설·상시 전체 리뷰·끝없는 모델 간 토론은 도입하지 않는다.
- 구현 시 decisions.txt, progress.txt, loop-plan.txt의 관련 절도 실제 동작과 맞춰 갱신한다. 이 문서 추가만으로 하네스가 구현된 것으로 표시하지 않는다.

## 완료 확인과 보고

- PowerShell 문법과 기존 BOM 등 실행 조건을 확인한다.
- PC에서 한 회차의 인계→시험→검증→결과 기록을 확인한다. 실패 반환·Codex 사용 불가 시 복귀 경로는 통제된 모의 실패로도 검증하되 실제 한도 시험과 구분해 기록한다.
- 진행 중 사용자 작업·실제 플레이 월드에 영향을 주지 않고 기존 전용 시험 환경을 사용한다.
- 구현·검증한 커밋, 시험 결과, 남은 미확인 사항을 history.md와 progress.txt에 기존 형식으로 남긴다. 클라우드 컴파일이나 모의 시험을 실제 게임 PASS로 바꾸어 적지 않는다.
- 기준 측정이 아직 부족하면 측정 및 기존 작업을 이어갈 수 있게 만들고, 분업 도입 조건과 다음 할 일을 남긴다. 미구현 단계는 완료라고 하지 않는다.
- 루프 재개는 사용자가 PC에서 실행을 지시한 범위에 맞춰 처리한다. 이 문서 등록만으로 stop 파일을 삭제하거나 루프를 재개하지 않는다.

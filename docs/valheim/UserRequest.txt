- 요청 하나 = 한 덩어리. 첫 줄이 요청의 이름 역할을 한다. 덩어리 사이는 빈 줄.
- 요청 사이에는 빈 줄을 꼭 넣는다(붙여 써도 따로 보려고 하지만 빈 줄이 확실하다).
- 답은 history.md 맨 위에 "### 요청 · 날짜 · 이름"으로 온다: 회차는 시작하자마자 답부터 쓰고, 돌고 있는 회차가 있으면 15분 백업 때 확인해
  답 전용 세션이 15~30분 안에 답한다(질문은 바로 답, 일은 "[받음 시각]"을 앞에 붙여 두고 다음 회차가 맨 먼저 함). 가져간 요청은 루프가 이 파일에서 지운다.
- 루프가 멈춰 있으면(사용자 확인 필요·할 일 없음·진척 없음 등) 이 파일이 바뀌면 5분 안에 다시 돈다. 아주 멈추려면 loop-stop.txt를 만든다.
- 같은 걸 다시 시키려면 새로 쓴다(지워진 요청은 history.md에 남아 있다).

코드 정리 — 관련 작업 때 작게 (사용자 요청 2026-10-23, 큰 리팩터링 아님)
- 1순위(물건 복제·소실 막음): CraftStep.Take()가 실제로 꺼낸 개수를 돌려주게 한다. Chests.TryEdit 실패나 개수 확인 뒤 변동으로 덜 빠지면 부르는 쪽(PortalBuilder 2곳, MachineStep 3곳)이 되돌리거나 멈춘다. 일부러 덜 빠지게 하는 시험으로 재료 총량을 확인한다.
- 귀환 통일: FarmJob.UpdateHome·GraveJob.UpdateHome(거의 같은 코드, 180초 뒤 TeleportTo 성공 여부를 안 보고 상자 단계로 감)과 GatherJob.LeaveCrypt의 깃발 순간이동을 WorkerAI.TeleportHome()(성공 확인)·RestHere()(실패 시 쉬기)로 맞춘다.
- 저장 접근: WorkSaves가 ExploreJob 비공개 필드 4개(m_dirX 등)를 AccessTools 문자열로 읽는다 → ExploreJob에 저장용 internal 속성이나 메서드를 둔다.
- 낡은 설명: "[게임 시험 안 됨]"(7개 파일 8곳)·"다음 조각"(PlanJob·Departures)은 그 파일을 고칠 때 실제 시험 여부를 확인하고 고친다. 이것만 하려고 회차를 쓰지 않는다.
- GatherJob은 파일 크기만으로 나누지 않는다. 실패 처리와 상태 저장의 일관성을 우선한다.
